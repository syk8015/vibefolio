## 2. 핵심 설계

### 2.1 업로드는 서버가 한다 (v1은 맥 워커)
1. 업로드는 브라우저·화면·AI가 필요 없는 API 호출뿐이다. 맥이 할 이유가 없다.
2. 맥이 꺼져 있어도 예약 시각에 올라간다(백로그의 "맥이 꺼지면 전부 멈춤" 제거). 타겟이 영미권이라 게시 시각이 한국 밤·새벽이 된다.
3. 보안 방향과 맞는다 — 맥엔 `WORKER_SECRET` 하나만, 서비스롤·R2·RESEND 키는 서버에만(서버 중계).
   SNS 토큰을 맥 키체인에 두는 v1안이 오히려 이 방향에서 벗어난다.

실행: 5분 점검 크론(`/api/cron/health`)에 게시 단계를 붙인다 — `lib/handoffReminders.ts`처럼 붙이면 cron-job.org에 새로 등록할 게 없다.
- 틱마다 짧은 호출만: ① 예약 시각이 된 포스트를 원자적으로 집어 컨테이너 생성 ② 이미 만든 컨테이너 상태 확인 → `FINISHED`면 게시.
  처리를 기다리며 함수를 붙잡지 않는다(다음 틱에 이어간다).
- 🔴 점검 크론이 느려지면 cron-job.org가 실패로 세다가 작업을 꺼버릴 수 있다(응답 한도 **확인 필요**). 게시는 응답을 먼저 보내고 뒤에서 돌린다
  (`after()` — 이 Next 버전 문서 `node_modules/next/dist/docs/`로 확인 후). 유튜브 업로드(R2에서 받아 resumable 업로드로 흘리기)는 틱당 1건.
- 중복 게시 막기: 컨테이너 id·업로드 세션 주소를 **게시 전에** `external_id`에 적고, 재시도는 같은 id로 이어간다.

### 2.2 토큰은 "연결" 버튼으로 받는다
- `/admin/promo`에 [스레드 연결]·[인스타 연결]·[유튜브 연결]. OAuth 한 번 → 서버 콜백이 토큰을 받아 저장.
  **토큰이 사람 손·채팅·터미널을 한 번도 안 거친다**(전역 시크릿 규칙에 가장 맞는 모양).
- 저장: 새 표 `promo_channel_auth` — RLS 켜짐·정책 없음 = 서비스롤 전용(`promo_posts`와 같은 패턴).
  값은 앱 단 암호화(AES-GCM, 키 = env `PROMO_TOKEN_KEY` 1개 — 값은 로컬에서 만들어 `vercel env add`로 바로 흘려 넣고 화면에 안 찍는다).
- 메타 토큰(인스타·스레드)은 60일 → 크론이 50일째쯤 자동 갱신. 갱신 실패 = 관리자 경보 메일(점검 크론 경보 경로 재사용).
- 유튜브: 새 GCP 프로젝트(로그인용과 분리), OAuth 동의화면 **"프로덕션" 게시** 필수(테스트 상태면 7일마다 토큰이 죽는다).
  미인증 앱 경고 화면이 뜨지만 쓰는 사람이 본인 1명이라 무관.

### 2.3 예약 대기열

- 캡션은 사람이 쓴다(AI 캡션 폐기 결정 그대로). **고정 꼬리는 채널별로 자동**: 스레드 = 추적 링크, 인스타·유튜브 = "링크는 프로필에" + 해시태그(유튜브 `#Shorts`). 백로그의 "정적 캡션 템플릿"이 이것.

## 4. 디스패치 연결 구상

### 4.1 관제탑(`/admin`) — "자동 일꾼" 칸
- 버튼: [조사 맡기기](주제 한 줄) · [순찰 지금]. code-review는 버튼을 두지 않는다(반복 금지 규칙 — 필요하면 CLI로 1회).
- 흐름: 버튼 → 서버가 `dispatch_jobs`에 넣음 → 맥 dispatchd가 20초마다 서버에 묻고 집어감 → `claude -p` →
  보고서 본문을 서버로 올림 → 관제탑 목록(제목·한 줄 요약·상태) → 눌러서 읽기. 관제탑은 폰 대응돼 있어 폰에서 읽힌다.
- 🔴 `local-runner/dispatch/QUEUE-DESIGN.md`의 "러너가 관리자 권한 열쇠를 키체인에서 읽는다"는 **서버 중계 불변식과 충돌**한다
  (맥엔 `WORKER_SECRET` 하나). → `/api/worker/dispatch/{claim,finish}`를 `requireWorker`로 만들고, 표는 서비스롤 전용,
  관제탑은 `requireAdmin` 라우트로 읽고 쓴다.
- 맥이 꺼져 있으면 "대기 — 맥이 켜지면 시작"(dispatchd 하트비트 한 칸). 한도 게이트는 그대로, 보류면 이유를 목록에 표시.
- 파일 대기열은 지우지 않는다(인터넷 없이 도는 유일한 길 — QUEUE-DESIGN "옮기는 순서").

### 4.2 홍보 클립 페이지(`/admin/promo`)
- 업로드 예약·연결 버튼은 여기(§2). **디스패치(AI)는 업로드에 끼지 않는다** — 판단할 게 없는 일(v1 원칙 1).
- 디스패치가 끼는 곳 = **소재 공급**: 새 일꾼 `meme-scout`가 문구 후보 N개를 산출물로 → 태그라인 풀 위 "후보" 줄 →
  사람이 [채택]/[버림] → 채택분은 촬영 대기열로. 지금 풀은 코드(`lib/loggedInTaglines.ts`, 로그인 메인 헤드라인과 공용)라
  후보를 받으려면 DB 표로 옮기거나 후보 표를 따로 둔다.
- 선행: 밈 저작권 기준(사용자). 제안 기본값 = "글자만 — 밈의 말투·상황만 빌리고 남의 그림·영상·음악·캐릭터는 안 쓴다".
  우리 클립은 원래 무음·글자+로고라 이 기준과 맞는다.
- 나중: "성적 모으기" — 플랫폼 조회수를 가져와 `PerfRank`에(인스타·유튜브는 게시물별 링크가 안 눌려 조회수가 유일한 게시물별 지표).

### 4.3 사이트 순찰
- AI 순찰 도구(WebFetch)는 GET만 되고 응답 헤더를 못 본다 → "조용히 깨지는 3곳" 중 ②(`POST /api/mcp` 401 + `WWW-Authenticate`)는
  확인 불가, ③(`/@핸들` 영상 태그)은 글로 바꾸는 동안 사라지고 핸들도 안 정해져 있다.
- **09-25 적용**: 3곳을 점검 크론(`/api/cron/health` 4c, `lib/sitePatrol.ts`)에 넣었다 — 5분마다, 요청당 5초·동시, 깨지면 기존 경보 메일(6시간 중복 억제).
  손으로 돌리기: `npx tsx scripts/probe-site-patrol.mts`. AI 순찰 [순찰 지금] 버튼은 아직 없음(필요할 때만).
- 09-24 실측(3곳 직접 두드림): ①② 정상. ③은 **검사할 대상이 없다** — 공개 작품이 사이트 전체 2개, 영상 붙은 것 0개.
  → 크론 검사는 "영상 있는 공개 작품이 있으면 그 주인 페이지로, 없으면 건너뜀"으로 짠다(안 그러면 매 틱 헛경보).
- 짤 때 주의: ①은 클로드가 실제로 읽는 `/.well-known/oauth-authorization-server`(rewrite)로 두드려야 rewrite 고장도 잡힌다.
  `/@핸들`은 `/핸들`로 307 — 리다이렉트를 따라간 뒤의 페이지를 본다. 코드상 `<video>` 요소는 서버 HTML에 그려지고 `src`만 화면에서 붙는다(`useSrcWhenVisible`) → 태그 유무를 HTML로 판정할 수 있을 것으로 본다(**미확인** — 영상 있는 공개 작품이 생기면 실측).
  ③의 대상은 "무대 첫 작품(대표작, 없으면 정렬 첫 번째)이 `<video>`로 그려지는 주인"만 고른다 — 영상 작품이 있어도 무대 첫 작품이 영상이 아니거나 유튜브(iframe)면 명함에 `<video>`가 없는 게 정상이라서.

## 5. v1에서 그대로 가져가는 것
1. 업로드는 AI가 아니라 신뢰 코드가 한다 — AI에 SNS 토큰을 주지 않는다.
2. 같은 클립+채널 = 같은 포스트(링크가 갈라지면 성적 반토막). `promo_posts.channel`은 `PROMO_CHANNELS` 라벨 그대로.
3. 조용히 실패하지 않는다 — `failed` + 이유 + 경보. 일시 실패는 `attempts < 3` 재시도, 인증 만료는 즉시 실패 + 경보.
4. 존중할 결정(v1 §13): AI 캡션 폐기 · 캡션 클립당 1개 · 실촬영 배치는 사용자가 꺼내기 전 제안 금지 · 지운 PostRow·PostComposer 부활 금지.

기다림이 긴 건 **유튜브 심사 하나**다. 그런데 신청서(support.google.com/youtube/contact/yt_api_form)가
OAuth 로그인 화면·업로드 화면·개인정보처리방침 유튜브 절·홈 화면 **스크린샷**과 GCP 프로젝트 번호를 요구한다
(09-25 확인, 영상은 불필요) → 프로그램이 먼저 있어야 신청된다. 기간은 공식 문서에 없음(경험담 몇 주~몇 달).
그래서 **유튜브 연결·업로드를 메타보다 먼저 만드는 순서 변경을 제안**했다(사용자 답 대기).

1. 유튜브(구글) — `nookframehq@gmail.com`으로
   1. console.cloud.google.com → 새 프로젝트(예: `nookframe-publish`, 로그인용 프로젝트와 분리)
   2. API 라이브러리 → `YouTube Data API v3` 사용
   3. OAuth 동의 화면: 외부 · 앱 이름 Nookframe · 개인정보처리방침 `https://nookframe.com/privacy` · 약관 `https://nookframe.com/terms`
      → **앱 게시(프로덕션)**(테스트 상태면 7일마다 토큰 만료. "확인되지 않은 앱" 경고는 본인 1명이라 무관)
   4. 사용자 인증 정보 → OAuth 클라이언트 ID(웹) → 리디렉션 `https://nookframe.com/api/admin/promo/connect/youtube/callback`
   5. ID·비밀값은 채팅 금지 → Vercel env `YOUTUBE_CLIENT_ID`·`YOUTUBE_CLIENT_SECRET`. 프로젝트 번호는 비밀 아님(알려주기).
   - Claude 몫: 연결·업로드 화면 + 개인정보처리방침 유튜브 절(YouTube API 약관·구글 개인정보처리방침 링크·삭제 방법) → 스크린샷 → 신청서 답안 준비.
