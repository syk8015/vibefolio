# Nookframe 화면·글 기준 (한 장)

새 화면·새 주소·새 창·새 문구를 만들거나 고칠 때 **먼저 읽는다.** 여기 없는 것은 같은 종류의 가장 최근 화면을 따른다.
정한 날짜는 괄호 안. 이 기준을 바꾸려면 사용자가 정하고, 이 문서를 같이 고친다.

## 0. 철학 — 보여 주고, 설명하지 않는다. 원할 때만 보여 준다. (09-23)

- 바이브 코더는 AI가 한 중간 과정을 들여다보지 않는다. 화면은 할 일 하나와 결과를 보여 준다. 까닭·자세한 내용·고를 것은 접어 두었다가 누르면 연다(`components/FoldToggle.tsx`).
- 작품이 주인공이다. 누가 만들었는지보다 무엇을 만들었는지가 먼저다.

## 1. 덜어내기 기준 (10-01, 모든 화면)

1. **한 화면엔 한 가지 일.** 상태마다 진한 버튼은 하나다.
2. **대신 해 주기.** 시스템이 할 수 있는 일은 설명하지 않고 한다. 사람이 정해야 하는 것만 남긴다.
3. **군더더기 빼기.** 뜻이 안 바뀌는 낱말은 지운다. 같은 문장은 두 번 쓰지 않는다. 곁말은 버튼 이름에 녹인다. 버튼 이름은 누르면 일어날 일이다("공개하기", "프롬프트 복사").

**늘 보이게 둔다(접지 않는다).** 되돌릴 수 없는 일(삭제·공개), 누가 보는지(나만·누구나), 실패. 짧게 쓰되 정확하게 쓴다. 쉬운 말이 위험을 가리면 안 된다(토스 '외상구매' 교훈).

## 2. 모양 — 종이와 잉크

- **나누기:** 선 대신 옅은 채움으로 나눈다. 바탕은 `--surface-soft`, 마우스를 올리면 `--surface-soft-hover`, 고른 것은 `--surface-active`에 굵게. 테두리는 기능 선에만 쓴다(목록 사이 가는 선, 탭 밑줄, 입력칸 포커스, 틀린 칸).
- **글자 크기(PC):** 17은 질문·큰 제목, 15는 단계·버튼, 14는 부제·펼친 글·실패 문구, 13은 접힌 줄·묶음 이름·태그다. **낱말은 13 이상이고, 12 이하는 숫자만 쓴다.**
  - 예외: 꾸밈 그림 속 글자, PC 명함 카드, 도구 아이콘 글자, × 같은 기호.
- **글자 진하기:** 잉크 하나에 단계를 둔다. 제목 1.0, 본문 0.82, 보조 0.6이다. 0.6 밑으로 내리지 않는다.
- **색:** `app/globals.css`의 변수만 쓴다(`var(--text-primary)`, `--surface`, `--danger` …). 다크 모드는 종이를 어둡게 한 것이지 뒤집은 것이 아니다. 그래서 직접 쓴 색(`#fff`, 검은 그림자, 빨강 hex)은 다크 모드에서 틀어진다.
  - 그림자는 `--shadow-card-*`를 쓴다.
  - `--blue` 위 글자는 `var(--bg)`로 쓴다.
  - 예외: 늘 어두운 무대·영상 위 표시는 그 자리에 까닭을 적는다.
- **버튼:** 진한 버튼은 글자만큼의 알약이다. 곁의 안내 줄과 함께 가운데에 둔다. 가로를 꽉 채운 막대는 안 된다.
  - 고르는 목록(예: Google로 계속하기)은 꽉 채워도 된다.
  - 폼 아래 저장 버튼은 오른쪽에 둬도 된다.
- **글꼴:** 본문은 `var(--font-nunito)`(실제 글꼴은 Inter), 세리프 제목은 `.vf-serif-display`, 고정폭은 `.vf-mono`. 다른 글꼴은 쓰지 않는다.
- **미리보기는 진짜와 같게:** "방문자에게 이렇게 보여요"라고 했으면 공개 화면과 같은 조각·같은 비율로 그린다.
- **공용 부품 먼저:** 같은 모양을 인라인으로 다시 만들지 않는다. 부품이 기준에 어긋나면 부품을 고친다(모든 화면이 같이 바뀐다).
  - globals.css의 `.vf-*` 클래스: `.vf-button-primary`·`-ghost`·`-text`, `.vf-icon-button`, `.vf-input`, `.vf-selectable`, `.vf-row-button`, `.vf-spinner`
  - 부품: `components/Modal.tsx`, `components/Segmented.tsx`, `components/FoldToggle.tsx`, `components/theater/StageMarks.tsx`
- **폰 화면은 동결(09-27~):** 폰 전용 모양은 고치지 않는다. 375px에서 깨지지만 않게 한다. 폰 기준은 따로 하는 폰 작업에서 정한다.

## 3. 말

- **해요체.** 짧고 능동적이고 긍정적으로 쓴다. "~시겠어요?" 같은 과한 높임은 쓰지 않는다. 명사를 늘어놓지 않고("대본 검토") 문장으로 쓴다("대본을 확인해요").
- **이름:**
  - 공개 페이지 전체는 **프레임**이다("내 프레임", "프레임 수정"). 영어는 frame / your frame.
  - **명함**은 페이지 안의 명함 카드와 대시보드 명함 탭에만 쓴다.
  - 서비스를 설명하는 문장에서는 **라이브 포트폴리오**라고 한다.
- **실패는 사람 말로 쓴다.**
  - 서버·검사기의 영어 문장, 칸 경로(`scenes[2].line`), HTTP 숫자를 화면에 그대로 내지 않는다.
  - 틀린 칸 바로 밑에 무엇이 틀렸고 어떻게 고치는지 한 줄로 쓴다.
  - AI에게 줄 긴 문장은 [프롬프트 복사] 안에만 둔다.
  - 서버 실패 응답은 `{ error, code, field }`(`lib/apiError.ts`)이고 `body.message`는 없다. `body.error`를 읽는다.
- **두 언어:** 화면 글은 사전(`lib/i18n/dictionaries/ko.ts`·`en.ts`)에 키로 둔다. 주 대상이 영어권이라 영어도 짧고 자연스럽게 쓴다.
  - 키를 더하거나 바꾸면 `docs/i18n-review.md`에 줄을 더한다.
  - 한국어 글을 바꾸면 `npm run font:subset`을 돌린다.

## 4. 만드는 순서

- 큰 화면 변경은 **시안 먼저** 만들고 사용자가 고른다. 확인은 실서버에서 한다(라이트·다크, PC 1440, 폰 375는 깨짐만).
- **새 화면 점검표:**
  1. 이 화면의 한 가지 일은 무엇인가?
  2. 진한 버튼이 하나인가? 그 이름이 결과를 말하나?
  3. 지워도 되는 설명이 남았나?
  4. 되돌릴 수 없는 일, 누가 보는지, 실패가 보이나?
  5. 다크 모드로 봤나?
  6. `npm test`가 통과하나?

## 5. 자동 검사 — `scripts/probe-ui-rules.mjs` (`npm test`에 들어 있다)

- **재는 것:**
  - `size`: 13 미만 글자
  - `color`: 직접 쓴 색
  - `border`: 1px 테두리·고리 상자
  - `font`: 정해 둔 글꼴 밖
  - `bar`: 꽉 찬 진한 버튼
  - `raw-error`: `body.message`, HTTP 숫자
  - `tone`: 합니다체·과한 높임
  - `name`: 페이지를 명함이라 부름
  - `ko-jsx`: 사전 밖 한국어 화면 글
- **기준선:** `scripts/ui-rules-baseline.json`은 2026-10-02에 있던 어긋남이다. 검사는 **새로 생긴 것만** 막는다.
- **맞는 예외:** 그 줄이나 바로 윗줄에 `// ui-allow: <규칙> <까닭>`을 적는다. JSX 안에서는 `{/* ui-allow: … */}`로 쓴다.
- **고쳐서 줄었으면** `npm run ui:baseline`을 돌린다. 기준선은 줄어들 때만 다시 쓰이고, 늘리려 하면 거절된다. 새 어긋남을 기준선에 넣어 숨기지 않는다.
- 사람이 봐야 하는 것도 있다. 버튼 이름이 결과를 말하는지, 설명이 군더더기인지, 영어가 자연스러운지는 위 점검표로 본다.
