# Dispatch(가칭) — 원격 지령 총괄 작업장 설계 v2

> 2026-07-14. v1(원격 지령 채널) 위에 사용자 피드백 반영:
> **관제 범위를 바탕화면 전체 프로젝트 + 배포된 사이트로 확장**하고,
> 성장 분석을 **다단계 딥리서치**로, 홍보를 **"업로드만 누르면 되는" 완제품 꾸러미**로 격상.

## 0. v1 → v2 변경 요약

| | v1 | v2 |
|---|---|---|
| 관제 범위 | cluadehelp 폴더 중심 | **프로젝트 레지스트리** — 바탕화면 전체 + 배포 사이트(nookframe.com 등) 총괄 |
| 잡 형태 | 단일 실행만 | 단일 + **레시피(다단계, 체크포인트·재개)** |
| growth | 단발 아이디어 보고서 | **4단계 딥리서치**: 현황→경쟁 발굴→비교→전략·수익화 백로그 |
| 홍보 | 초안 텍스트 | **promo-pack 꾸러미**: 플랫폼별 카피 + 카드뉴스(PNG 렌더) + 숏폼 대본 |
| 산출물 후처리 | 없음 | **포스트프로세서** — dispatchd(신뢰 코드)가 HTML→PNG 렌더 등 수행 |

v1의 골격(폰 지령→CF inbox→dispatchd→워커, HMAC 서명, 사용량 게이트, opus 4.8 기본,
맥북 야간 전원, `pmset -c sleep 0`)은 그대로 유지.

## 1. 아키텍처 (v2)

```
[폰: 컴포저] ──서명된 잡──▶ [CF inbox Worker] ◀──20s 폴링── [Mac: dispatchd]
 프로젝트 선택 + 타입                                          │
 + 텍스트 + 시간                                               ├ ① 로컬 큐 (즉시/at/every)
                                                               ├ ② 사용량 게이트 (스테이지 사이에도)
[폰: 푸시] ◀── 결과·경보 ──────────────────────────────────────┤ ③ 워커 실행 (단일 or 레시피)
                                                               │    └ 레지스트리 컨텍스트 주입
                                                               ├ ④ 포스트프로세서 (PNG 렌더 등)
                                                               └ ⑤ outbox 꾸러미 + 로그
```

## 2. 프로젝트 레지스트리 — 총괄의 핵심 (신설)

`~/Dispatch/registry/<이름>.md` — 관제 대상마다 카드 1장. 잡은 `params.project`로 참조하고,
dispatchd가 해당 카드(+ 홍보 틀 자산)를 워커 프롬프트에 주입한다.

```markdown
---
name: nookframe
local: ~/Desktop/vibefolio              # ⚠️ 폴더명은 리네임 전 이름 그대로(의도적) — 제품명과 다름
repo: syk8015/vibefolio (main, Vercel 배포)
live: https://nookframe.com
status: 라이브 운영·개선 중
---
한 줄: <서비스 설명>
타깃: <핵심 사용자>
경쟁/유사: <알고 있는 것들 — growth가 갱신>
수익 모델: <현재 / 후보>
```

- 홍보 틀 자산: `registry/<이름>/promo-frame/` — 톤·금지어·해시태그·브랜드 컬러·카드뉴스 HTML 템플릿.
  **틀은 사용자가 잡고, 워커는 틀 안에서 생산한다.** (초기 틀 자체를 첫 잡으로 생성시킬 수도 있음)
- **보안 규칙**: 레지스트리가 접근 범위의 단일 원천. T2 워커는 카드에 적힌 `local` 경로만 읽을 수 있고,
  미등록 폴더(예: `TOSS auto/`)는 어떤 워커도 접근 불가.
- 초기 등록 후보(바탕화면 실측): **nookframe(=`~/Desktop/vibefolio` 폴더)**, claudehelp(notify·위젯·워밍업),
  zenith-dashboard, ai-saas-dashboard 등 — 등록 시점에 사용자가 선별.
  `nookframe-takes-0712/`(홍보용 화면녹화 mp4 — promo-pack 소재 후보)와
  `nookframe-mobile-meishi/`(명함 실험)는 라이브 아님, 등록 제외.

## 3. 잡 모델 (v2: 레시피 추가)

```jsonc
{
  "v": 2,
  "id": "j_20260714_a3f2",
  "type": "growth",                    // 워커 enum
  "params": { "project": "nookframe", "prompt": "수익화 중심으로" },
  "when": { "mode": "at", "t": "2026-07-15T02:00:00+09:00" },
  "model": "opus",
  "ts": …, "nonce": "…", "sig": "…"
}
```

- **단일 잡**: `claude -p` 1회 → 보고서 1개
- **레시피 잡**: 스테이지 목록을 순차 실행. 각 스테이지 = 독립된 `claude -p`,
  이전 산출물 파일을 다음 스테이지 입력으로 전달(워크스페이스 공유)
  - 스테이지 사이마다: **게이트 재확인** + **체크포인트 저장**(`queue/<id>.json`에 진행 스테이지 기록)
  - 한도 도달·타임아웃 시 중단 → 다음 윈도우에서 **이어서 재개** — 무거운 잡이 밤을 넘겨도 안전
  - 각 스테이지의 예상 규모가 다르면 모델도 스테이지별 지정 가능(검색 라운드는 sonnet, 종합은 opus 등 — 기본은 opus)

## 5. growth 딥리서치 레시피 (사용자 요구 반영)

"단발 아이디어 보고서"가 아니라 **여러 번 정밀 검색으로 파고드는 4단계**:

1. **S1 현황 파악**: 라이브 사이트 주요 페이지 정독(WebFetch) + 레지스트리 카드 + (옵션) 리포 구조 훑기
   → "지금 무엇이고, 뭐가 부족한가" 현황 메모
2. **S2 경쟁 지형 발굴**: 키워드·카테고리·타깃 관점을 바꿔가며 **다각도 웹서치 여러 라운드**
   → 경쟁·유사 서비스 목록(각각의 특징·가격·채널)
3. **S3 정밀 비교**: 겹치는 항목 / 차별점 / 우리에게 빠진 기능 / 포지셔닝 → 비교 매트릭스
4. **S4 전략 종합**: 성장 채널(SEO·커뮤니티·SNS)·수익화(가격·플랜·전환 퍼널) 방향 +
   **우선순위 붙은 실행 백로그**

산출: `outbox/<날짜>/growth-nookframe/REPORT.md + BACKLOG.md`.
S2~S3에서 발견한 경쟁사 목록은 레지스트리 카드에 반영 제안(다음 실행이 더 똑똑해짐).

## 6. promo-pack 홍보 꾸러미 레시피 (사용자 요구 반영)

목표: **"기초 틀은 내가, 생산은 에이전트, 나는 업로드 버튼만."**

1. **S1 소재 수집**: 레지스트리 카드 + 라이브 사이트 최신 상태 + (T2 옵션) 최근 변경사항에서 홍보 소재 추출
2. **S2 카피**: promo-frame의 톤·해시태그 규칙대로 **플랫폼별 본문 N개**(X/Threads/인스타 캡션) → `posts.md`
3. **S3 카드뉴스**: promo-frame의 HTML 템플릿 기반 슬라이드 생성 → `cards/*.html`
   → **[후처리] dispatchd가 Playwright로 PNG 렌더** → `cards/*.png`
4. **S4 숏폼 대본**: 촬영·녹화 지시 포함 장면 구성 + 대본 → `video-script.md`

산출: `outbox/<날짜>/promo-nookframe/` 꾸러미 — 검토 후 바로 업로드 가능한 상태.

**포스트프로세서 원칙(신설)**: 렌더링·변환·압축은 에이전트가 아니라 **dispatchd(신뢰 코드)**가 한다.
에이전트 권한(Bash 등)을 늘리지 않고 산출물 품질만 올리는 장치. PNG 렌더는 Phase 1b에서 추가
(그 전까지 카드뉴스는 HTML을 브라우저로 열어 저장).

## 9. 사용량 게이트 — **v3 (2026-09-18 실측 개정, 구현 완료)**

> 근거: `memory/reference-claude-usage-pattern.md`. 로그 52,656건 + 게이지 표본 25,000행 실측.
> **선제적 게이트는 Dispatch의 유일한 구조적 우위다** — subsched·Codeman 등 유사 시스템은
> 전부 429를 맞고 나서 대응하는 반응형이다. 여기를 강화한다.

잡 시작 전(+ 레시피 스테이지 사이마다) 조회해 아래 순서로 판정한다:

| # | 검사 | 기준 | 왜 |
|---|---|---|---|
| ① | **실행 시간대** | 반복 잡은 **04:00~06:00**에만 시작 | Vive는 20~01시 피크. 04~10시가 유일한 유휴 구간. 06시 이후 시작하면 5h 창이 11시 피크까지 물린다 |
| ② | 주간 하드 백스톱 | 잔여 <30% 보류 | 마지막 방어선 |
| ③ | **하루 예산** | `예상비용 ≤ 0.5 × (주간잔여%p ÷ 리셋까지 남은 일수)` | 단일 임계값은 시점을 못 본다. 잔여 30%가 리셋 6일 전이면 위험, 1일 전이면 여유 |
| ④ | 5시간 | 잔여 <25% 대기 | **옛 10%는 죽은 게이트였다** — 69개 창 중 2개만 해당해 사실상 발동한 적이 없다 |
| ⑤ | 모델별(scoped) | 잔여 <50% | 기존 유지 |

- 예상비용 = `est_requests[타입] × 0.0148%p` (실측: 주간 1%p ≈ 요청 67건)
- ⚠️ **`now`/`at` 잡은 ①을 건너뛴다** — 사용자가 직접 넣은 건 의도대로 실행한다
- 잡·스테이지 전후 사용량 스냅샷 로깅 → `est_requests`를 실측으로 교정할 것
- 🔴 **무거운 잡은 주 2~3회가 상한.** 딥리서치 1회 ≈ 주간 3~9%p이고, 3주 중 1주가 94%까지 찼다.
  매일 돌리면 주 21~62%p로 확실히 넘친다

## 11. 구현 계획 (v2)

**Phase 1a — 코어 + 단일 워커 (relay 없이)**
1. 레지스트리 스키마 + 초기 카드 2장(nookframe, claudehelp) — 경로는 사용자 확정
2. dispatchd: 큐(즉시/at/every) + 게이트 + 직렬 실행 + 푸시 + `dispatch add` CLI
3. 단일 워커 3종: research / site-monitor / code-review → **로컬 e2e**
4. launchd + `pmset -c sleep 0` 설치 스크립트

**Phase 1b — 레시피 엔진**
5. 스테이지 실행기(체크포인트·재개·스테이지간 게이트)
6. growth(4단계) + promo-pack(카피·카드뉴스 HTML·대본)
7. 포스트프로세서: Playwright HTML→PNG
8. 실전: **새벽 4시** growth-nookframe 예약 → 아침 보고서·백로그 확인
   (⚠️ 원안의 "밤 2시"는 실측상 Vive 피크 시간이라 폐기 — §9 참조)

**Phase 2 — 원격 채널 + 폰 열람**
9. inbox Worker(HMAC·nonce·TTL) + QR 페어링 + 컴포저(프로젝트 선택 포함)
10. outbox 뷰어(폰에서 카피 복사·카드 저장)

**Phase 3 — SNS 연동**
11. 자격증명 금고 설계 → engage-draft(댓글 수집·답글 초안)
12. 승인 흐름 포함 sns-post / 계정 운영(계정 개설 자체는 사람 — 인증 절차상)
